# 维护、可靠性与基本安全

软件开始被使用以后，环境、数据和需求都会继续变化。维护的任务，是让系统在这些变化中仍然能够被理解、观察和调整。

## 运行结果需要被观察

日志记录某些事件和上下文，指标把运行情况汇成可以持续观察的数字，例如请求耗时和失败数量。更复杂的系统还会把跨组件的调用联系起来，帮助理解一次操作经过了哪些地方。

这些信息服务于具体问题。收集了很多日志却无法找到相关请求，或者保存了大量数字却不清楚它们在统计什么，都不等于已经具有良好的观察能力。

对普通读者而言，重要的是理解“软件在运行”和“我们能知道它运行得怎样”还需要不同机制。

## 可靠性包含失败时的行为

网络可能暂时不可用，依赖服务可能返回错误，程序也可能需要重启。可靠的设计并不是假定失败永远不会发生，而是明确等待多久、哪些情况可以重试、重复操作怎样处理，以及无法完成时怎样反馈。

同时，不能对任何错误都无限重试。重复请求可能增加负担，也可能重复产生业务动作。重试、超时、去重和回退需要与实际操作的含义相匹配。

## 备份与恢复是同一件事的两面

备份保存某个时点可用于恢复的内容；恢复则证明这些内容在需要时能够重新使用。只看见一个备份文件，不足以知道它是否完整、是否包含必要配置，以及能否在目标环境中读回。

版本仓库通常记录代码，数据库备份记录数据，密钥与环境设置可能又由其他系统管理。恢复流程需要知道这些边界，而不能把“代码已经上传”理解成整个服务都有备份。

## 安全首先涉及信任与权限边界

来自用户、网络、文件或其他服务的内容，进入程序后应当按它实际的角色处理。输入数据不应仅凭外观就变成可以任意执行的指令；一个已经登录的身份，也不应自动获得所有对象的访问权。

前面介绍的参数化查询（防范 **SQL 注入**）、服务端授权（防范 **越权访问 IDOR**）和会话管理（配合防范 **CSRF**），都在维护这些边界。页面展示外部内容时，也需要采用合适的输出转义方式，避免把普通文字误当成可执行页面内容（即防范 **跨站脚本攻击 XSS**）。常见的 Web 安全风险分类可参阅 [OWASP Top 10](https://owasp.org/www-project-top-ten/)。

权限应与实际工作需要相匹配（最小权限原则）。一个只需要读取记录的组件，或者一个开发阶段的 AI 智能体，如果同时拥有修改或删除全部生产数据的能力，就扩大了错误或凭据泄露可能影响的范围。

## 更新需要知道改变了什么

依赖更新可能修复问题，也可能改变行为。系统升级、证书变化和接口调整，也会影响长期运行的软件。维护需要记录版本与配置，理解变化，并进行针对性的检查。

“一直不更新”与“每次都立即更新所有东西”都不能代替具体判断。应看变更原因、影响范围、可用证据和恢复办法。这里的知识帮助读者理解维护工作的存在，不要求把个人小示例按大型系统的方式运维。

## 把问题描述留给下一位读者

维护还包括说明软件的用途、关键边界、已知限制和重要设计理由。清楚的记录减少后来的人重复猜测，也帮助 AI 在修改时取得真实上下文。

当某次操作失败，用户需要的是准确的状态与下一步，而不是一条不符合实际的成功提示。能够说明“发生了什么、尚未确认什么”，也是软件可靠性的一部分。

这一套认识同样适用于 AI 辅助开发：生成速度提高以后，运行环境、权限和数据仍然存在，解释它们的责任也仍然需要有人承担。

> [!TIP]
> **实战提示**：上线应用前确认两件事：**付费 API 后台是否设置了每月消费上限（spend limit）？线上数据库的数据是否保存在持久化存储而非容器临时文件里？**
