# 与 AI 讨论需求和修改

与 AI 协作时，描述需求、提供上下文、观察修改和反馈结果，是相互联系的过程。目的不是记住一种固定的提示词格式，而是让双方讨论同一个问题，并能够判断事情是否做成。

## 从使用场景说到可观察的行为

“增加读书进度功能”说明了方向，但还留下许多选择。更具体的描述可以是：

> 我希望在一本书的详情页填写已读页数。总页数为 200 时，填写 60 并保存，页面应显示 30%；重新打开这本书仍能看到 60。已读页数必须是 0 到总页数之间的整数，输入不合要求时说明原因。

这段话交代了位置、输入、正常结果、持久化要求和一部分边界。它仍可能没有回答账号共享、离线操作等问题，但已经可以用来判断一项具体功能。

如果某个选择会明显改变结果，应当说明或讨论。反过来，按钮内部的变量名这类低影响实现细节，通常可以交给实现者决定。自然语言协作需要明确结果，也需要给合理的实现判断留出空间。

## 提供能帮助定位的上下文

修改已有项目时，最有用的信息通常包括：当前行为、期望行为、相关入口、环境，以及已经观察到的错误。能够访问项目的助手，应结合实际文件确认；只能聊天的助手，则需要你提供适当片段。

比较下面两种反馈：

> 保存坏了，修一下。

> 在书籍详情页把已读页数从 48 改成 60，点击保存后出现成功提示，但刷新页面又变成 48。浏览器里能看到一次保存请求，响应状态为 500。其他书也会出现同样情况。

第二种描述没有直接断言“数据库坏了”，而是给出了一条可以调查的现象链。500 表明服务端报告了错误，但具体原因仍需要查看相关日志和代码。若提供日志或请求内容，应保留诊断所需信息，去掉真实凭据与无关个人数据。

## 用一段完整过程理解协作

下面通过一段三步交互，展示如何把现象定位、修改方案与验证边界交代清楚：

**使用者：** 修改阅读进度保存功能。现在保存失败也会显示成功。希望保存成功后再更新确认状态；失败时保留输入，并让人知道没有保存。请结合现有项目实现，说明改动和验证结果。

**助手在读取相关文件和日志后：** 前端发送请求后就显示成功，没有等待并检查保存结果。我会让界面根据响应区分成功与失败，并保留失败时的输入。后端仍负责检查页数与访问权限。

**助手在修改并验证后：** 修改了保存事件处理和状态显示。成功响应时展示确认结果；失败响应时显示错误并保留 60。已经检查这两种响应下的页面行为。当前测试环境没有可用数据库，因此尚未确认真实数据写入及刷新后的读回。

这里最关键的地方，是把“做出的修改”“取得的证据”“尚未确认的环节”分别说明。最后一句限制意味着功能还没有完成全部验证；它也给后续工作提供了清楚的起点。

## 阅读修改时，顺着数据与行为看

面对差异视图，可以先看哪些文件承担了不同职责：界面发生什么变化，输入在哪里校验，请求发往哪里，持久化发生在哪里。这条路线与前面的 [Web 操作全过程](23-web-journey.md)相同。

如果一项局部修改同时替换了框架、改写登录方式或改变了数据结构，就需要理解这些扩大范围的动作与当前目标有什么关系。合理的重构可能帮助修复问题，但范围越大，重新确认的行为通常也越多。

小步修改的价值，在于容易把结果与原因联系起来。在日常开发中，一套稳健的**人与 AI 协作流程**通常包含以下几步：
1. **动手前留存检查点**：运行 `git status` 确认工作区干净，或先做一次 `git commit` / 新建分支；
2. **先对齐计划再改代码**：对较复杂的任务，先让 AI 阅读相关文件、列出实施计划和受影响的文件（Plan 模式），人工确认方向后再让它修改；
3. **一次聚焦一件事**：每次只推进一个清晰的功能点或修复一个具体问题，避免把界面改版、数据结构调整和依赖升级混在同一轮修改里；
4. **结合运行证据与 `git diff` 验收**：运行程序或测试命令查看真实输出，并用 `git diff` 检查改动范围（对删除文件、新增外部依赖、修改权限/登录逻辑、改动测试断言等操作始终人工确认）；
5. **及时提交或果断回退**：验证通过就立即 `git commit`；如果 AI 在同一个问题上反复打补丁、越改越乱，不要在坏状态上继续堆砌对话，而是用 `git restore` 退回上一个干净提交，整理好关键信息后**开启一个新会话**重新开始。

## 检查应围绕承诺的结果

“代码能够运行”检查了一部分问题；“保存后刷新仍能看到更新”又检查了其他环节。验证哪些行为，要从需求反推，不能只根据现有测试恰好覆盖什么来决定。

对阅读进度的例子，正常保存、无效输入、服务端失败，以及重新读取后的状态，都与最初的承诺有关。不同检查可以由函数测试、接口检查或浏览器操作承担。相关概念可回看[测试在检查什么](29-testing.md)。

AI 对自己的修改再解释一遍，可以帮助理解，却没有自动产生新的运行证据。请它说明具体执行了什么、观察到了什么，比反复要求“保证完全正确”更有用。

## 把有效信息留在下一次还能找到的地方

一次修改完成后，值得保留的是需求边界、影响较大的决定、验证方式和已知限制。临时推测得到证伪后，应及时更正，避免它成为下一次工作的错误前提。

对于长期使用的软件，版本记录保存修改，项目文档解释运行与设计，问题记录保存未解决现象。这些材料既帮助人协作，也能成为 AI 的上下文。好的协作最终留下的是可以继续理解和维护的项目。

> [!TIP]
> **实战提示**：把五步协作变成肌肉记忆：**① 先 `git commit` 存档 → ② 让 AI 先出计划 → ③ 小步修改单一目标 → ④ 运行验证并看 `git diff` → ⑤ 成功就提交，跑偏就回退重开对话。**
