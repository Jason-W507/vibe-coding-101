# 数据保存、数据库与 SQL

页面上的数字变化，只说明当前界面的状态发生了变化。要让它在刷新、关闭程序或换一台设备后仍然可用，还需要明确的保存机制。

## 运行状态与持久数据

内存适合承载正在使用的信息，但程序退出或环境变化后，不能仅依靠原来的运行状态。文件、数据库和其他持久存储机制，让信息能够跨越一次运行保留下来。

数据库并不一定在远方。它可以与应用运行在同一台机器上，也可以作为独立服务存在；某些数据库引擎还可以嵌入应用进程。重要的是它提供怎样的数据组织、查询和管理能力，而不是它的机器外形。

把内容写入一个文本文件，也是一种保存方式。随着数据关系、查询、并发修改和可靠性要求增加，专门的数据库系统能够提供更多支持。是否使用哪种系统，应由实际需要决定。

## 用表描述一类记录

关系数据库经常用表组织数据。一行表示一条记录，一列表示其中某类属性，表的结构和约束说明允许保存什么。

| id | title | total_pages | read_pages |
| --- | --- | --- | --- |
| 1 | 计算机基础 | 200 | 48 |
| 2 | 软件开发入门 | 160 | 0 |

这里的 `id` 用来稳定地区分记录，称为主键。标题可能修改或重名，所以不能只因人容易记住标题，就假定它适合作为所有关联的依据。

如果另有一张阅读日志表，可以记录“哪本书，在什么时间，读到了多少页”。日志中的书目编号把两类记录联系起来；外键等机制可以帮助约束这种关系。一个概念是否应该成为单独的表，要看它的含义、关系和变化方式。

## SQL 描述需要的数据操作

SQL 是与关系数据库交互时常见的语言。下面是一组可以在 SQLite 中执行的完整示例，用于展示建表、写入和查询。它也保存为[随书 SQL 示例](../../examples/sql/reading-notes.sql)的一部分。

```sql
CREATE TABLE books (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    total_pages INTEGER NOT NULL CHECK (total_pages > 0),
    read_pages INTEGER NOT NULL
        CHECK (read_pages >= 0 AND read_pages <= total_pages)
);

INSERT INTO books (id, title, total_pages, read_pages)
VALUES (1, '计算机基础', 200, 48),
       (2, '软件开发入门', 160, 0);

SELECT id, title, read_pages, total_pages
FROM books
WHERE read_pages < total_pages
ORDER BY id;
```

查询会返回上述两条仍在阅读中的记录。`WHERE` 表示筛选条件，`ORDER BY` 明确排序。没有指定排序时，不应仅凭某次看到的排列就假定数据库承诺了固定顺序。SQLite 对[建表](https://www.sqlite.org/lang_createtable.html)与[查询](https://www.sqlite.org/lang_select.html)分别有完整语法说明；不同数据库的具体语法仍可能有差异。

`NOT NULL` 和 `CHECK` 是这个示例选择的约束。它们表达“总页数必须已知且大于零，已读页数在允许范围内”。现实中若要容许总页数未知，就需要重新设计规则。数据库不会替人决定这种业务含义。

这里还有一个与具体数据库有关的边界：普通 SQLite 表里的 `INTEGER` 声明会影响类型转换，却不等于所有输入都被严格限制为整数。例如范围内的小数仍可能存入这张示例表。若业务要求只能填写整数，应把这个要求落实到输入校验及合适的数据库约束中，不能只看列名后面的类型文字。详见 [SQLite 的数据类型说明](https://www.sqlite.org/datatype3.html)。

## 修改、删除与关系变化

除了插入和查询，程序还可以更新或删除记录。这里经常需要明确条件：想更新一本书的进度，就要准确指向那条记录，而不能无意中修改整张表。

数据结构本身也可能变化。例如后来要区分纸质书和电子书，就需要决定新字段如何表示、既有数据怎样处理，以及旧版本应用是否仍能理解它。这类受控的结构变更通常称为迁移，属于软件演进的一部分。

## 用户输入应当作为数据传递

程序经常需要把用户输入用于查询。正确的基本方向，是把查询结构和数据值分开交给数据库驱动，通过它提供的参数机制处理，而不是把输入直接拼进 SQL 命令文本。

这样才能避免把原本应当表示书名等内容的输入，当成查询语法的一部分。参数通常用于数据值；动态选择表名、列名等结构时，还需要相应的受控规则，不能机械套用同一种占位方式。[PostgreSQL 的参数化执行说明](https://www.postgresql.org/docs/current/libpq-exec.html)展示了这种结构与数据分离的思想。

数据库解决的是一组明确问题。数据是否真正在预期位置保存、谁有权读取、并发修改怎样处理、怎样备份，仍需要应用和运行环境共同安排。看到一个“保存成功”的界面时，可以追问它究竟确认了哪一步。
