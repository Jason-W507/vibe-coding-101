# 设备怎样在网络中找到彼此

在浏览器输入一个网址，后面可能涉及很多机器之间的通信。为了理解这个过程，先把网址里不同部分的职责分开。

## 一个网址包含不止一个名字

下面是一个用于说明结构的虚构网址，`.example` 用于示例，不对应本教程提供的在线服务：

```text
https://notes.example:8443/books/17?view=summary#progress
```

| 部分 | 这里表达什么 |
| --- | --- |
| `https` | 使用的 URL 方案，这里对应 HTTPS |
| `notes.example` | 要联系的主机名 |
| `8443` | 显式指定的端口 |
| `/books/17` | 路径，由服务按自己的规则解释 |
| `?view=summary` | 查询参数 |
| `#progress` | 片段标识，常供浏览器定位页面内部位置 |

片段部分通常不随 HTTP 请求发送给服务器。路径也未必对应服务器磁盘上的某个真实目录。服务器可以通过自己的路由规则解释 `/books/17`，例如把它视为“编号为 17 的书”。关于主机与端口的组成，可参阅 [MDN 的 URI authority 说明](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Authority)。

## IP 地址与域名怎样配合

IP 地址参与网络层面的寻址。域名提供一种更适合人和服务组织使用的名字。DNS 是把域名等名字映射到相应记录的分布式系统，其中一项常见作用是获得可联系的 IP 地址。

DNS 不会把整个网址“翻译成网页”。它不负责决定你的账号能看到哪本书，也不执行页面中的业务代码。同一域名可能对应多个地址，不同访问条件下也可能得到不同结果；已经获取的结果还可能被缓存。

知道地址以后，仍然需要网络把数据送到对应位置。实际通信会经过本机网络、路由设备以及可能存在的其他中间环节，并受各层协议与规则约束。

## 端口把机器上的服务区分开

一台机器可以同时运行多个需要通信的程序。端口是协议寻址中的一部分，用于帮助把通信交给相应的服务端点。它不是磁盘里的文件夹，也不是屏幕上的某个物理插口。

HTTP 和 HTTPS 有常用的默认端口，所以网址中常常可以省略。如果某个开发服务监听其他端口，就可能需要把它明确写在地址中。访问了正确的机器但错误的端口，也可能联系不到期望的服务。

“服务已经启动”还应继续问：它监听哪个地址和端口？从哪个网络环境访问？本机能够访问，不等于所有外部设备都能访问。

## localhost 指向访问者所在的环境

`localhost` 是用于回环访问的特殊名称。对通常的本机访问而言，它表示联系自己这个环境上的服务。因此，你把 `http://localhost:8000` 发给朋友，朋友打开后尝试联系的通常是朋友自己环境中的服务，而不是你的电脑。[RFC 6761](https://www.rfc-editor.org/rfc/rfc6761.html#section-6.3)规定了 localhost 的特殊处理。

容器、虚拟机和远程开发环境会增加一层需要辨认的边界：你看到的浏览器与运行服务的程序，可能并不处在同一个网络环境中。这时不能只看地址文字相同，就假定它们指向相同对象。

## 客户端和服务器是交互中的角色

发起某次请求的一方是客户端，处理并响应它的一方是服务器。浏览器是常见的客户端，但脚本和其他服务也可以发请求。

服务器既可以指承担角色的程序，也常被用来指承载这些程序的机器，语境决定具体含义。同一台普通电脑既可以运行客户端，也可以运行服务端；后端还可能继续作为客户端访问另一个服务。

当页面打不开时，可能是名字解析、连接、端口、服务运行状态或应用处理出现问题。把这些位置区分开，就能理解为什么“重写页面代码”不一定能解决一个实际发生在连接之前的故障。
