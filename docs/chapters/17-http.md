# 请求、响应与 HTTP

HTTP 为 Web 通信规定了一套请求与响应的语义。它让双方能够说明要操作什么、采用什么方式、提交哪些信息，以及结果是什么。

## 一次请求里有什么

下面是简化的 HTTP/1.1 文本示意，省略了与具体连接和完整报文有关的其他细节：

```http
GET /api/books/1 HTTP/1.1
Host: notes.example
Accept: application/json
```

`GET` 是请求方法，路径指向服务所定义的资源，`Host` 提供主机信息，`Accept` 表示客户端希望收到的内容类型。真实通信不要求人手工拼出这几行；浏览器和库会处理相应表示与传输过程。

请求还可以带消息体，例如提交一份 JSON 数据。方法、路径、头部和消息体各有职责，不能只看一个网址就知道调用需要的全部信息。

## 方法表达操作语义

GET 用于获取资源表示，POST 常用于提交需要处理的数据。PUT 请求用提交的表示创建或替换目标资源的状态；PATCH 提交如何修改资源的说明，常用于局部修改；DELETE 请求移除目标资源与相应地址之间的关联。DELETE 并不单凭方法名就保证后台已经物理擦除了所有副本。具体业务怎样映射到这些方法，还要看 API 的设计；PATCH 的语义另见 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)。

GET 在协议语义上属于安全方法，不应被用来安排用户没有预期的业务修改。对其他方法是否可以放心重试，也要结合它们的语义与具体服务约定。知道一个方法名字，还不足以推断系统在重复请求时一定采取什么业务行为。

## 响应告诉你哪一层发生了什么

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"title":"计算机基础","read_pages":48,"total_pages":200}
```

状态码帮助表达请求的处理结果类别。2xx 表示成功类别，3xx 与重定向等情况有关，4xx 表示请求相关错误类别，5xx 表示服务端错误类别。各个具体状态码还有细分含义。

`200` 也不能自动证明业务逻辑完全正确。如果服务把错误数字算出来后照常返回成功响应，传输机制并不会替你判断那个数字是否满足需求。阅读响应时，还要看内容与接口约定是否一致。

头部中的 `Content-Type` 帮助接收方判断内容应怎样解释。JSON 是表示结构化数据的一种文本格式，不是数据库，也不专属于某一种编程语言。

## 一个页面往往有很多请求

打开页面可能先获取 HTML，随后获取样式、脚本、图片，再请求业务数据。部分资源可能来自缓存，部分内容可能已由服务端生成，不同应用的组织方式会有所不同。

因此，某个页面能打开，却无法保存记录，并不矛盾。负责显示页面的请求成功了，负责保存的另一次请求可能失败。浏览器的网络观察工具可以把这些交互分别展示出来，后面的调试部分会解释如何看待这些证据。

## HTTPS 保护的是通信过程

HTTPS 在 HTTP 通信中使用相应的加密与身份验证机制，帮助保护传输内容的保密性、完整性，并验证连接对端的服务身份。

接收内容的服务器仍需要处理这些业务数据。HTTPS 也不会自动修复“甲用户可以读取乙用户的记录”这样的授权问题。它解决的是通信中的一组问题，应用自己的业务和权限逻辑仍需正确设计。HTTP 与 HTTPS 的语义可参阅 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

HTTP 的不同版本还可能采用不同的底层传输安排，所以本教程把请求与响应的含义放在主线，而不把“所有 HTTP 永远都通过同一种传输协议”当成定义。

## 无状态不表示网站不能记住你

HTTP 的基本请求语义不会自动为每个访问者维持一份连续的应用记忆。网站可以通过 Cookie、会话和数据库等机制建立跨请求的状态关系。

登录后为什么下一次请求还能识别身份，要从这些额外机制解释，不能仅凭“使用了 HTTP”就得到答案。接下来的前端、后端和登录专题会把这些层次逐步接起来。
