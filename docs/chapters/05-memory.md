# 内存里的数据去了哪里

程序会记住光标位置、已经打开的记录和正在计算的中间结果。这些运行中的信息需要占用内存。讨论内存时，至少要区分三个问题：程序通过什么位置访问数据，这个位置对应哪块实际资源，以及这份数据需要保留多久。

## 地址是访问位置的表示

可以先把内存想象成很多可寻址的位置。程序通过地址及访问规则取得或更新某段内容。地址本身不解释内容：相同的一组字节，如果按不同的数据类型读取，含义可能不同。

在现代通用操作系统里，普通应用通常使用**虚拟地址**。操作系统与硬件把进程使用的虚拟地址映射到实际内存等资源。两个进程中出现相同的地址数字，不意味着它们一定在访问同一份数据。

这种安排帮助系统隔离进程、管理映射和实施权限。程序也不必直接操心自己的每一块数据当前位于哪一根内存条上的哪个位置。[OSTEP 的地址空间章节](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf)介绍了这一层抽象。

```mermaid
flowchart LR
    A[进程 A 的虚拟地址] --> M[受系统管理的地址映射]
    B[进程 B 的虚拟地址] --> M
    M --> P1[实际内存中的一部分]
    M --> P2[实际内存中的另一部分]
```

这张图只表达地址与资源之间存在映射。共享内存、文件映射和权限等情形还会使关系更丰富。

## 分配与释放是什么意思

程序需要保存一批新数据时，要取得可以使用的空间。它可能通过语言运行时、内存分配器以及操作系统等层次完成这件事。释放则表示某块空间不再用于原先的用途，可以按相应机制被重新利用。

例如，打开一张图片可能需要容纳解码后的像素；关闭图片后，这些空间有机会被回收。程序仍然存在，并不要求曾经使用过的每一份数据都永久留着。

这里还存在几种不同的“用完”：业务上不需要了、语言运行时已经能够判断它不再被使用、分配器把空间留给未来复用、系统实际减少了这部分物理资源占用。这些时刻不必完全相同。所以，删除一个变量名字或关闭一份内容后，系统监视器里的数字不一定立即下降。

## 栈和堆是什么

很多执行环境使用**调用栈**记录函数调用过程中的信息，例如返回位置和某些局部状态。一次调用进入时建立相应记录，返回后结束这一层调用。不断嵌套的调用因此形成层次关系；如果函数无限递归调用自己而没有退出条件，就会耗尽调用栈空间，触发**栈溢出**（例如 Python 的 `RecursionError` 或 JavaScript 的 `RangeError: Maximum call stack size exceeded`）。

需要更灵活生命周期的数据，常由另一套动态分配机制管理，通常与**堆**这一术语相关。例如，一份记录可能在创建它的函数结束以后仍被其他地方使用。

这是理解常见实现的入口，不是“所有语言的所有局部变量都一定在栈上”的统一规则。编译器优化、解释器实现以及语言的对象模型都会影响实际安排。这里的堆内存，也不要与算法中名为“堆”的数据结构混为一谈。

## 谁决定数据可以回收

有的语言要求程序员明确管理资源的生命周期，有的通过所有权规则或自动回收机制管理。**垃圾回收**通常通过运行时机制识别不再需要保留的对象，并在适当的时候处理它们。

但“自动回收”不等于程序不会无限增长。例如，程序把每次请求的数据都继续放进一个长期存在的全局列表中。从运行时看，这些对象仍然可以被访问；即使业务上已经不需要它们，也无法被回收——这就是常见的一种**内存泄漏（memory leak）**。此外还要记住，无论栈还是堆，都属于当前进程的内存空间：**一旦进程结束，操作系统会回收它的全部内存**；想要跨越进程生命周期保留的数据，必须写入文件或数据库（见[第 20 篇](20-database.md)）。

相反，在允许手动管理内存的环境里，如果空间释放后代码还沿着旧引用访问它，就可能产生不正确的行为。不同语言和运行时提供不同程度的检查与约束。理解这些问题，有助于看懂“泄漏”“越界”“失效引用”等错误描述，而无需现在就学习某一种语言的全部底层规则。

## 虚拟内存不是“拿磁盘当内存”的同义词

虚拟内存首先是一套地址和资源管理抽象。当物理内存紧张时，系统还可能把部分暂时不用的内存页移到磁盘上的交换空间（如 Windows 的页面文件 `pagefile.sys`、Linux 的 `swap`），也可能采用内存压缩等机制。是否启用这些机制、怎样使用它们，与系统和配置有关。

把虚拟内存直接定义成“硬盘上的额外内存”，会漏掉地址隔离、映射和保护等核心作用。即使没有把内容换到磁盘，进程仍然可以使用虚拟地址空间。

## 为什么一小段代码会用很多内存

源代码文件的大小，与执行时要处理的数据规模不同。一小段程序可以要求读取几百万条记录，或者创建大量中间对象。图片、压缩文件和数据库结果展开后，也可能占用比原始文件更多的空间。

看到内存不足，应该继续查看数据量、对象生命周期、并发任务数量和环境限制。磁盘剩余空间、进程地址空间限制以及物理内存压力也要分别理解。只有分清这些层次，才能知道应该减少一次处理的数据、改变保存方式，还是调整运行环境。
