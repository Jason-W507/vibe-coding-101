# AI 编程与 Vibe Coding

读到这里，我们已经可以把“让 AI 帮我做一个软件”拆开来看：AI 可能帮助描述需求、生成代码、运行检查、分析错误，也可能参与发布和维护。这些活动与前面讨论的软件开发工作一一对应。

## 先说清楚本教程怎样使用这些词

这里我们用 **AI 编程（AI coding）**泛指借助 AI 理解、生成、修改和检查代码等活动。

**Vibe Coding** 的用法则存在差异。Andrej Karpathy 在 2025 年 2 月提出这个词时，描述了一种主要通过自然语言要求模型修改、总是直接接受改动（Accept All）、较少细读差异（diff）而靠观察运行结果与粘贴报错来推进的方式，并指出这种方式“对一次性的周末小项目还算不错（not too bad for throwaway weekend projects）”。这里对原帖内容的介绍依据 Simon Willison 文章中的转引；Willison 自己也主张把这种不读代码的做法与会审阅、理解代码的 AI 辅助工程区分开。[原文转引与作者的区分](https://simonwillison.net/2025/Mar/19/vibe-coding/)

另一些介绍更宽泛地用 Vibe Coding 指自然语言驱动的开发，也把审阅、理解和测试生成代码纳入其中。例如 Google Cloud 的说明就采用较宽的范围。[Google Cloud 的术语说明](https://cloud.google.com/discover/what-is-vibe-coding)

因此，两个人都说自己在 Vibe Coding，实际做法可能差别很大：一个只观察页面效果，另一个会阅读差异、检查数据流并运行测试。讨论时，把具体做法说明白，比争论某个标签更有用。本教程保留 **Vibe Coding 101** 这个名称，学习重点是理解开发活动背后的知识。

## AI 可以参与哪些工作

AI 对开发的帮助不只发生在“生成第一版代码”的瞬间。你可以给它一段错误信息，请它说明调用关系；让它阅读一个模块，找出数据在哪里被修改；给出已经明确的规则，请它实现并检查相应行为。

| 活动 | AI 可能提供的帮助 | 判断结果时要看什么 |
| --- | --- | --- |
| 理解已有项目 | 解释目录、调用关系、运行入口 | 解释能否指向真实文件与代码 |
| 实现需求 | 生成或修改代码、配置与文档 | 行为是否满足需求，修改范围是否合适 |
| 查找问题 | 提出原因假设、读取日志、尝试修复 | 假设是否有证据，原问题是否可复现并得到修复 |
| 检查与维护 | 补充检查、分析差异、说明变更 | 检查覆盖什么，哪些风险尚未验证 |

“可能”取决于所使用的产品和工具权限。一个只能聊天的界面，可以提出代码但未必能够修改本地文件；一个接入终端与项目目录的助手，才有条件执行更多步骤。下一篇会展开这个区别。

## 用 AI 写软件，与给软件加 AI 功能

假设你让 AI 写了一个计算剩余页数的函数。生成完成后，这个函数按固定规则做减法；普通用户使用它时，不需要再次调用模型。这是 **AI 参与了软件的开发**。

如果你在读书记录工具里加一个“AI 提炼读书笔记摘要与标签”按钮，用户每次点击时，你的软件都要在运行过程中通过网络调用大模型接口（LLM API），再把模型返回的内容展示或保存起来。这是 **AI 成为了软件的一个运行组件**。两种情况可以同时存在，但不能混为一谈：一个项目是“AI 写的”，不代表它运行时必须联网调用模型；反过来，只要你的软件在运行时调用了大模型，就需要在架构上处理好以下四个核心环节：

- **消息角色结构（`system` / `user` / `assistant`）**：调用大模型 API 时，发送的通常不是一团不分彼此的字符串，而是一组带角色的消息列表——`system`（或 `developer`）消息用来交代固定规则与输出格式要求，`user` 消息承载用户本次输入的读书笔记内容，`assistant` 消息则代表模型此前的回复（多轮对话时需由程序按需拼接历史消息一并发送，因为模型 API 本身通常是无状态的）。
- **后端代调、限流与费用护栏**：大模型 API 按消耗的输入与输出 token 计费。调用模型的私有 API Key 必须放在你自己的**后端服务**中，由前端先请求你的后端接口、后端检查用户登录与调用频率限制（Rate Limiting）后再转发给模型服务商，并在服务商后台配置每月用量硬上限（Spend Limit），防止接口被恶意刷取导致高额账单。
- **流式输出（Streaming / SSE）**：模型生成几百字摘要可能需要数秒钟。如果等整段话全部生成完才一次性返回 HTTP 响应，用户会盯着空白页面以为卡死了。因此 AI 应用常使用**流式传输（Streaming，常见基于服务端推送事件 SSE，Server-Sent Events）**：模型每算出几个词（token），后端就顺着同一条连接立刻推给前端，在界面上呈现出像打字机一样逐字浮现的效果。
- **结构化输出（Structured Outputs / JSON Schema）**：如果只是把回复展示给人看，普通自然语言就够了；但如果你的程序接下来要把模型提炼出的 `{"summary": "...", "tags": ["科普", "计算机"], "score": 5}` 自动拆开存入数据库的对应字段，只靠在提示词里写“请只返回 JSON，不要说废话”往往不够稳妥——模型偶尔多加一句“好的，这是结果：”或漏掉一个引号，就会让程序的 `json.loads()` 直接报错崩溃。现代模型 API 提供了**结构化输出（Structured Outputs，传入预定义的 JSON Schema 格式约束）**或工具调用模式，从生成机制上约束模型严格按指定字段和类型返回，后端解析后再做一次业务校验即可安全入库。

## 自然语言让入口改变，也让隐含选择更容易被忽略

“帮我保存阅读进度”在人与人之间也不够精确。保存在当前浏览器、一个本地文件，还是服务器数据库？不同设备是否共享？是否需要登录？这些选择会改变系统结构。

AI 很可能为没有说清的地方补出一个方案。补出的方案可能合理，也可能与使用场景不符。页面能够点击，只能说明某些交互已经存在；保存按钮变绿，也不能独自证明数据已经可靠写入。

前面的基础知识让你能够追问具体事实：请求发到哪里？后端确认了什么？刷新页面之后为什么还在，换设备后为什么不在？这些问题比“再高级一点”“再完善一点”更容易引出可检查的改动。

## 理解到什么程度才有帮助

你不需要先独立写出所有代码，才能从 AI 编程中受益。对于陌生修改，可以先弄清它的目的、输入与输出、影响的数据和运行位置，再逐步理解关键实现。

同时，检查深度应随影响而变化。一个只在当前页面内计数的小示例，与一个会修改他人共享数据的服务，需要的证据不同。后者涉及授权、失败状态、数据一致性与恢复，单看界面效果通常不够。

这也是本教程先介绍计算机与软件，再介绍 AI 的原因：工具能够缩短从想法到代码的距离，而这些基础概念帮助你判断，代码和预期的软件之间还差哪些环节。

> [!TIP]
> **实战提示**：如果只是一个周末自用的小脚本，只看运行效果完全没问题；但只要涉及**他人使用、长期维护、账号权限或真实资金/付费接口**，就必须把代码审查与边界验证加上。
