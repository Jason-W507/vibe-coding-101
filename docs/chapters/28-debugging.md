# 调试、日志与问题定位

调试是在证据支持下解释程序为什么没有按预期表现。修改代码是其中可能采取的一步，但在定位原因之前不断修改，容易把原来的问题与新变化混在一起。

## 把现象说成可以比较的行为

“保存坏了”还很模糊。更具体的描述是：输入 60 后点击保存，页面短暂显示成功，刷新后又变回 48；这发生在某个版本和某种登录状态下。

这段描述包含输入、动作、实际结果和原先期望。其他人或 AI 才能据此沿着前面介绍的完整 Web 流程查找线索。

复现不必等于复杂的测试工程。它首先是确认什么条件下能观察到同一现象，同时避免无关操作不断改变环境。

## 证据来自不同层次

浏览器开发者工具（按 `F12` 打开，重点查看显示报错与输出的 **Console** 面板，以及查看每个请求状态码、载荷与响应体的 **Network** 面板）、服务端终端日志，以及数据库查询结果，分别观察系统的一部分。

例如，看到服务端日志“已接收请求”，不能直接推断事务已提交；看到数据库里已经是 60，也不能推断当前页面已经读取了新值。记录中的措辞要与其发生位置对应。

如果多个请求交错进行，一个用于关联交互的标识可以帮助把同一条操作的记录联系起来。但日志仍应避免不必要地记录密码、令牌或完整敏感内容。

## 假设需要能被验证

对于刷新后恢复旧值的现象，可以提出不同解释：页面没有真正发送保存请求，字段名与接口约定不同，服务器拒绝了请求，或者刷新后读到了另一处数据。

下一步观察应该区分这些解释。例如查看请求是否存在、消息体是什么，以及响应怎样说明结果。如果响应指出字段不符合约定，就应该先理解那个具体不一致，而不是立即更换整个数据库。

减少一次验证中同时发生的变化，有助于知道究竟是哪项改变影响了结果。如果一个功能昨天还正常、今天突然坏了，可以先用 `git log` 和 `git diff` 对照最近几次提交改了什么，通过“二分排查”迅速锁定引入问题的改动。一次让 AI 重写界面、接口和存储，可能使问题暂时消失，却让原因更难追踪。

## 断点让运行中的状态可见

调试器可以在某个位置暂停执行，查看当前变量、调用关系，并逐步推进。这有助于区分“代码看起来会进入这个分支”和“这次实际进入了什么分支”。

不是每个问题都适合暂停观察。时序敏感或分布在多个服务中的问题，可能更依赖日志、指标或其他记录。不同工具提供不同观察方式，应由问题本身决定需要什么证据。

## 修复后检查原问题及相关行为

一个有说服力的修复说明，应当连接原因、改动和结果：原来为什么失败，改动为什么针对这个原因，同一条件下现在观察到了什么，以及重要的相邻行为是否仍然正常。

这比“没有报错了”包含更多信息。有时只是把异常捕获后忽略，有时是把失败提示隐藏起来，程序并没有完成原先需要完成的事情。

与 AI 协作时，可以让它先列出当前事实与待验证解释，选择能区分解释的观察，再做相关修改。人的职责不是事先知道答案，而是让整个推理过程始终与可见证据相连。
