# 索引与事务

认识表与查询以后，还会遇到两个经常一起出现的问题：数据很多时怎样较快找到需要的记录；一次业务操作涉及多次更新时，怎样管理它们之间的关系。索引和事务分别处理其中的重要部分。

## 索引为查找建立额外组织

如果经常按书名查找记录，数据库可以维护适合这种查找的额外结构，使某些查询不必完整扫描所有行。这种结构就是索引的一种用途。

目录页可以帮助人理解“额外组织帮助定位”的直觉，但数据库索引的实际结构、排序方式和访问过程比纸面目录复杂。常见实现会利用树等结构，具体能力取决于数据库及索引类型。

索引也占用空间。数据插入、修改或删除时，相关索引可能需要一起维护。查询系统还会判断某次查询是否值得使用某个索引；拥有索引，不代表每次都一定使用它，更不意味着索引越多越好。[PostgreSQL 的索引介绍](https://www.postgresql.org/docs/current/indexes-intro.html)说明了这类收益与成本。

## 事务把一组数据库操作放在同一边界内

假设更新读书进度时，既要修改书目的当前页数，又要新增一条阅读日志。如果只完成其中一步，记录之间可能出现不一致的业务状态。

可以把这两次修改组织在一个事务中。下面继续使用前一篇的 `books` 表，并为例子创建一张简单日志表：

```sql
CREATE TABLE reading_events (
    book_id INTEGER NOT NULL REFERENCES books(id),
    page INTEGER NOT NULL
);

BEGIN;
UPDATE books SET read_pages = 60 WHERE id = 1;
INSERT INTO reading_events (book_id, page) VALUES (1, 60);
COMMIT;
```

`BEGIN` 开始事务，`COMMIT` 提交其中的修改，放弃未提交的修改则使用 `ROLLBACK;`。真实程序还必须注意数据库在出错时的默认行为差异：例如在 SQLite 中，某条语句违反约束报错时，默认（`ABORT`）**只撤销这一条失败语句，并不会自动回滚整个事务**——如果代码捕获错误后没有执行 `ROLLBACK` 就继续执行 `COMMIT`，前面已经成功的 `UPDATE` 依然会被提交！因此，程序必须在事务内任一步骤报错时显式回滚。

示例只突出事务的组织方式。启用并执行外键等约束的具体要求也与数据库有关：例如 **SQLite 默认不开启外键约束检查**，必须在每次建立数据库连接后执行 `PRAGMA foreign_keys = ON;`（已包含在[随书 SQL 示例](../../examples/sql/reading-notes.sql)开头）才会真正生效。不能因为 SQL 中出现了 `REFERENCES` 约束名字，就跳过对实际配置的确认。

## ACID 描述什么

介绍事务时常见 ACID 这个缩写，可以先从它试图表达的目标认识：原子性关注事务内操作作为整体的结果；一致性涉及应被保持的约束；隔离性管理并发事务之间的影响；持久性关注已经提交结果的保留。

这些词不表示数据库会自动理解并证明所有业务规则。规则需要通过约束、代码和正确的使用方式表达；并发行为还受到隔离级别等条件影响。[PostgreSQL 的事务教程](https://www.postgresql.org/docs/current/tutorial-transactions.html)通过实例解释了事务边界。

例如，两个人都读取旧进度，再各自覆盖为一个新值，即使每个人都使用了事务，也仍需要考虑要怎样处理冲突。使用版本条件、合适的更新方式或其他协调机制，是更具体的设计问题。

## 事务的边界不会无限延伸

如果保存以后还发送了一封邮件，数据库回滚不会自动收回已经送出去的邮件。另一个独立服务完成的操作，也不必然受同一个数据库事务控制。

这意味着“出错就全部恢复原样”是一句需要说明范围的话。一个完整业务流程可能跨越数据库、网络和外部服务，程序必须为这些边界设计合适的重试与补偿方式。

阅读 AI 生成的保存逻辑时，可以看它把哪些操作放进了同一事务、怎样处理失败，以及是否误把外部动作也当成可以自动撤回。这样的边界认识，比仅检查有没有写出 `BEGIN` 和 `COMMIT` 更重要。

> [!TIP]
> **实战提示**：当一次操作需要同时修改多张表时，应放进同一个数据库事务，并确认**任一步骤报错时程序会显式执行回滚（`ROLLBACK`）**，而不是继续提交半成品数据。
