# Git、版本与协作

文件保存以后，只留下当前内容。开发中还经常需要知道之前是什么样、哪次修改改变了行为，以及怎样把几个人的修改联系起来。版本控制为这些变化建立可追踪的历史。

## Git 与托管平台分别负责什么

Git 是一种分布式版本控制系统。它把项目的版本历史保存在仓库中，许多操作可以在本地完成。GitHub 等平台可以托管 Git 仓库，并在其上提供 issue、评审和协作功能。[GitHub 对 Git 的介绍](https://docs.github.com/en/get-started/using-git/about-git)说明了两者关系。

因此，使用 Git 不等于已经把代码公开到网上；拥有一个托管平台账号，也不代表电脑中的任何文件都会自动被上传。

## 保存、暂存与提交

可以从三个位置理解日常工作：

| 概念 | 作用 |
| --- | --- |
| 工作区 | 你正在查看和编辑的文件 |
| 暂存区，也叫索引 | 准备放进下一次提交的内容状态 |
| 提交历史 | 已经记录下来的版本及其联系 |

保存文件改变工作区；暂存选择下一次提交准备记录的内容；提交建立一条版本记录。文件暂存以后如果又被修改，新修改不会仅因前面暂存过一次就自动进入那份已经准备的状态。

提交除了内容，还可以带有说明、作者和父提交等信息。简洁说明“这次为什么改”，有助于后来理解变化的目的。

## 分支与合并组织不同方向的变化

分支可以让不同工作沿各自的历史推进。它并不必然意味着手工复制一整份项目目录。Git 通过提交及引用之间的关系管理这些方向。

合并尝试把来自不同方向的变化组合起来。若系统无法自动决定某些内容怎样合在一起，就需要人处理冲突。但“没有文本冲突”也不保证组合后的行为正确：两个人可能修改不同文件，却对同一个接口产生了不兼容的理解。

```text
共同版本 ── 修改 A ──┐
         └─ 修改 B ──┴─ 合并后的版本
```

这张图表达历史关系；实际仓库还可以采用其他协作方式。

## 本地提交与远端同步

远端仓库是协作中的另一个仓库位置。`push` 等操作把相应提交和引用同步到远端；取得远端变化与把它们整合进当前工作，也有各自的动作。

因此，保存文件、创建提交、上传远端、把软件部署给使用者，是不同步骤。某个平台可以通过自动化把其中几步连接起来，但仍应知道具体触发了什么。

常见的只读观察命令包括：

```text
git status          查看当前改动与暂存状态
git diff            查看尚未暂存的工作区差异
git log --oneline   查看简洁的提交历史
```

右侧中文是说明，不是需要输入的参数。示例需要在已有 Git 仓库中使用；空文件夹不会自动拥有提交历史。命令的完整选项可查 [Git 官方文档](https://git-scm.com/docs)。

这里的 `git diff` 默认比较已跟踪文件的工作区与暂存区，不会把尚未跟踪的新文件内容全部展开。已经暂存的改动要查看相应的暂存差异，例如 `git diff --cached`。因此，某一种差异视图为空，也不能直接推断整个项目没有任何待记录的变化。

## 代码评审与 issue

Pull request 或 merge request 等协作入口，通常把一组拟合入的修改、讨论和检查结果放在一起。评审关注变更是否解决问题、是否引入其他影响，以及证据是否充分。

Issue 更适合记录问题、需求和讨论。对这份教程而言，读者可以用 issue 指出某一篇的概念不清、示例不符或缺少解释，并提供相应上下文。

## AI 修改后，版本差异是重要阅读材料

AI 的总结可能遗漏实际改动。差异视图让你看到它究竟删除、增加或修改了什么。它不替代对行为的检查，却能帮助你辨认范围：一个文字修改是否顺带改变了依赖，一个错误修复是否移除了原本需要的检查。

版本控制也不是完整的数据备份方案。仓库通常只记录被纳入其中的文件，不会自动保护数据库、运行中的状态或所有外部配置。了解记录边界，才能在需要恢复时知道自己真正保留了什么。
