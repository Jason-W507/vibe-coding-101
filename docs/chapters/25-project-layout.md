# 读懂一个代码项目的目录

AI 生成的项目往往包含许多文件。理解它们时，可以先按职责分类，而不必从第一行开始逐个读完。

下面是一份为了说明角色而设计的目录，文件名不代表统一标准：

```text
reading-notes/
├── README.md
├── src/
│   ├── main.py
│   ├── progress.py
│   └── storage.py
├── tests/
│   └── test_progress.py
├── assets/
│   └── cover.png
├── config.example.json
└── docs/
    └── decisions.md
```

## 源码、资源、配置和说明各做什么

源码表达程序逻辑。图片、字体等资源提供程序或界面需要使用的内容。配置描述在某个环境中怎样安排参数或行为。README 与其他文档说明项目用途、运行方式和设计背景。

测试文件检查程序在一定条件下是否符合预期。它们也是代码，但与直接提供业务功能的代码承担不同职责。某些项目还会有工具配置、依赖声明和构建脚本，帮助组织开发过程。

同一种职责在不同项目中可能使用不同目录名。看到 `src` 不应只记住缩写，更应去确认它在当前项目中是否真的放置源代码。

## 从入口追踪一条行为

**入口**是程序或工具开始执行某个流程的位置。它可能是指定文件、函数、框架约定或项目脚本，并不总叫 `main.py`。

如果想理解保存功能，可以先找界面动作或请求处理入口，再沿调用关系看到规则检查与存储操作。这样阅读一条具体路径，通常比无目标地读完整仓库更容易形成认识。

一份项目也可能有多个入口：网页、后台服务、命令行工具、测试与维护脚本可能分别启动。必须先说明你关心哪一种运行活动，才能判断“哪个文件是主程序”。

## 依赖与生成文件通常另有来源

依赖代码由包管理工具下载，构建产物由源码转换生成。打开一个 AI 生成的项目时，常会看到以下自动生成或工具管理的目录与文件：

| 常见名称 | 它是干什么的 | 能否手动删除 / 重建方式 | 是否提交到 Git |
| --- | --- | --- | --- |
| `node_modules/` | Node.js 下载安装的第三方包目录 | 可删，运行 `npm install` 重建 | **不提交**（体积大且可重建） |
| `.venv/` 或 `venv/` | Python 虚拟环境及已安装的第三方包 | 可删，重建虚拟环境并安装依赖 | **不提交** |
| `__pycache__/` | Python 自动生成的字节码缓存 | 可删，运行程序时自动重新生成 | **不提交** |
| `dist/`、`build/`、`.next/` | 构建打包产生的产物或框架缓存 | 可删，运行构建命令重新生成 | 通常**不提交** |
| `package-lock.json` / `uv.lock` | 精确记录依赖树版本的锁定文件 | 不手动编辑，由包管理工具维护 | 应用项目**应提交** |
| `.env` | 本地环境变量与私有 API 密钥配置 | **不能随便删**（内含本地配置） | **绝不提交**（只提交 `.env.example`） |
| `.git/` | Git 版本历史数据库（隐藏目录） | **绝不能删**（删了就丢失本地版本历史） | Git 自身数据 |

如果直接修改某个生成文件，下次构建可能把修改覆盖。反过来，也不能不加分辨地把所有不熟悉的目录当成可以删除的缓存。先理解来源，再决定该改哪里。

编辑器通常允许隐藏部分目录以便阅读。这是展示选择，不会改变它们是否参与程序运行。

## 配置影响行为，却不一定出现在函数里

程序连接哪个服务、使用哪个端口、采用什么运行模式，可能由配置文件、环境变量或启动参数决定。一份代码在两种环境下表现不同，有时就来自这些输入。

示例配置（如 `.env.example`、`config.example.json`）只展示需要提供哪些字段，不应包含真实凭据；包含真实密码和 API Key 的 `.env` 文件必须写入 `.gitignore` 排除在版本库之外。实际配置怎样加载，哪些值可以公开，哪些只能在服务端使用，都需要按项目的运行方式理解。

## 阅读 AI 的修改时，先看职责是否匹配

如果目标是改变提示文字，却出现了数据库结构、依赖版本和启动方式的大范围变化，应要求解释这些改动为什么与目标有关。相关改动不一定错误，但它们扩大了需要理解和检查的范围。

一个有用的项目说明，应当能指出关键目录的职责、主要入口以及常见行为经过的模块。等这张结构图清楚以后，再进入细节，代码文件就更容易从一堆陌生名称变成有联系的组成部分。
