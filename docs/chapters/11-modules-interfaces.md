# 模块、接口与程序组织

当程序变长，所有代码都挤在一个文件里会增加理解和修改的负担。模块把相关代码组织在一起，接口则说明其他部分怎样使用它。

## 文件的边界可以对应职责

假设一个小工具包含三类工作：计算进度、保存记录、显示结果。它们可以放在不同模块中，让需要调整显示的人先关注显示代码，让需要改变保存方式的人先找到存储代码。

模块不一定等于文件，但文件是许多语言中组织模块的常见方式。在 Python 中，一份普通 `.py` 文件可以作为源模块；模块也可能由其他形式提供。不能把“所有模块都是某种后缀的文本文件”当成跨语言定义。

把代码分成十个文件，也不会自动产生清晰结构。如果这些文件互相依赖、任意修改对方的内部状态，阅读时仍然必须同时理解它们。

## 接口是双方约定的边界

设想一个模块提供名为 `remaining_pages` 的函数。调用者需要知道它接收哪些值、返回什么、哪些输入无效，以及它是否会改变外部状态。这些信息共同形成使用约定。

接口可以是一组函数、一个对象提供的方法、一种文件格式，也可以是通过网络调用的服务。接口的概念比“一个网址”更广，后面的 Web API 是其中一种具体情境。

实现则是接口背后实际完成工作的代码。只要约定保持一致，实现有机会改变，而调用者不必同时知道所有内部细节。现实中是否真正兼容，还要考虑错误、性能和副作用等行为，而不只看函数名字是否相同。

## 导入让模块之间建立关系

Python 可以用 `import 模块`、`from 模块 import 名称` 或 `import 模块 as 别名` 等写法使用模块中的内容。阅读 AI 生成的导入语句时，可以先分辨它来自哪一类来源：**语言自带的标准库**（如 `math`、`json`、`pathlib`）、**通过包管理工具安装的第三方库**（如 `fastapi`、`requests`，见[第 26 篇](26-dependencies.md)），还是**当前项目自己的代码文件**。例如下面这个完整片段导入标准库模块：

```python
import math

print(math.isfinite(12.5))
```

输出 `True`，表示传入值是有限的数。这里重点是 `math.isfinite` 这种使用关系：先取得模块，再访问它公开的能力。具体函数的意义应以文档为准，不应只凭名字猜测。

导入还可能触发模块的初始化代码。普通 Python 源模块的顶层语句会在常规首次导入时执行，后续导入通常复用已加载模块。于是，把“启动服务”这样的动作直接放在一个容易被其他代码导入的文件顶层，可能造成意外行为；这也是为什么 Python 脚本常把直接运行时的入口代码放在 `if __name__ == "__main__":` 分支下（只有作为主程序直接运行时才执行，被其他文件 `import` 时不执行）。另外要注意，**不要把自己的 `.py` 脚本命名为与标准库或常用第三方库相同的名字**（例如把练习文件起名为 `json.py` 或 `random.py`），否则 `import` 时会优先导入你自己的同名文件而报“找不到属性”错误。相关机制见 [Python 模块教程](https://docs.python.org/3/tutorial/modules.html#more-on-modules)。

## 对象把数据与行为联系起来

对象是程序中组织信息和操作的一种方式。比如一份“阅读记录”可能具有标题、总页数、当前页数等属性，并提供更新进度的行为。类则是一些语言中用于定义这类对象结构和行为的机制。

不必为了说明每组数据都建立复杂的类。列表、映射、函数和简单模块都可以解决合适的问题。理解对象时，先看它保存了什么、允许外部做什么，以及内部状态怎样变化，比先背一组设计术语更有帮助。

## 好的组织让变化有位置可去

如果一个需求只是改变标题显示方式，却必须同时改动数据保存和进度计算，可能说明职责之间耦合得过紧。所谓耦合，可以先理解成某一部分的变化在多大程度上牵动其他部分。

减少不必要的牵动，有助于理解和维护；但拆分也有成本，会带来更多文件、调用和约定。模块设计因此是一种取舍。对刚接触 AI 编程的读者来说，一个实用入口是让 AI 先说明各模块负责什么、谁调用谁，再阅读它准备修改的具体位置。

> [!TIP]
> **实战提示**：新建练习文件时，**切勿用 `json.py`、`random.py`、`http.py` 等标准库名字命名自己的脚本**，否则导入时会遮蔽官方标准库导致报错。
